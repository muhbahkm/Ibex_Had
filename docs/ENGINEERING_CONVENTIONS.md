# IBEX HAD — Engineering Conventions

## Repository model

IBEX HAD is a TypeScript-first monorepo. The intended top-level layout is:

```text
apps/mobile
apps/web
packages/core
packages/contracts
packages/config
supabase/migrations
```

The financial domain must stay independent from presentation frameworks.

## Branching and pull requests

- `main` is production-grade and should remain releasable.
- Changes are developed on short-lived branches using prefixes such as `feat/`, `fix/`, `chore/`, `docs/`, `test/`, and `refactor/`.
- All material changes should reach `main` through a pull request.
- CI must pass before merge.
- Prefer squash merge so one pull request maps cleanly to one logical delivery.

## Commit convention

Use Conventional Commit style:

```text
feat(scope): description
fix(scope): description
chore(scope): description
docs(scope): description
test(scope): description
refactor(scope): description
```

Keep commits focused. Never mix unrelated product, database, and formatting changes in one commit merely for convenience.

## TypeScript

- Strict mode is mandatory.
- Avoid `any`; model unknown external input as `unknown` and validate it.
- Domain types should not depend on React, Expo, Next.js, or Supabase client types.
- Shared API contracts belong in a dedicated package once introduced.
- Monetary values must never use floating-point domain types.

## Financial domain rules

- Clients request business operations; they never write `ledger_entries` directly.
- Posted financial facts are immutable in financial substance.
- Corrections use explicit reversal/adjustment flows.
- Every critical write is idempotent where retry is possible.
- Balance caches are derivatives, never the source of truth.
- Currency balances remain separate unless a reporting conversion explicitly supplies rate, source, and timestamp.

## Database and migrations

- GitHub migrations are the source of truth for production DDL.
- Production DDL must not exist only in the Supabase SQL editor.
- Migration filenames use an ordered timestamp generated by the Supabase CLI when implementation begins.
- Every exposed table has RLS enabled in the same delivery that creates it.
- Policies are authorization rules, not only authentication checks.
- Financial database functions must be reviewed for privilege boundaries and transaction safety.
- After material DDL, run Supabase Security and Performance Advisors and verify the result.

## Environments

Planned environments:

- Local: developer Supabase stack and local clients.
- Preview/Development: isolated branch or project when introduced.
- Production: Supabase project `Ibex_Had v1` in Mumbai (`ap-south-1`).

Never point automated tests at production financial data.

## Secrets

- No secrets, database passwords, service-role keys, signing keys, or SMS credentials may be committed.
- Public/publishable client configuration may be exposed only when designed for public clients and still protected by RLS/domain authorization.
- Service-role or secret keys are server-only.
- Environment-specific secrets belong in the deployment provider / GitHub encrypted secrets / Supabase secrets, not source files.
- `.env.example` documents names only, never real values.

## Verification and Definition of Done

For a material change, completion means:

1. Code/migration committed in GitHub.
2. Lint, typecheck, and tests pass.
3. Backend/database changes are applied to the intended Supabase environment and verified.
4. Relevant Security/Performance checks pass.
5. Notion reflects important product/architecture/status changes.
6. No manual production drift remains.
